# Architecture

nx2android turns a player's own Switch game files into an Android app. The player picks the game's folder, clicks **Port**, and gets an APK plus the game's data, which the tool can install on a connected device. Every game the tool supports is a **game profile**; everything all games share is the **core**.

```
gui/  (PySide6 desktop app)
  │  runs `python -m porter port … --progress json`, draws the JSON events
  ▼
porter/  (headless port pipeline, also a CLI)
  │  inputs → extract → rewrite → shaders → host → apk → data pack → [install]
  │  reuses nxnative/scripts/build_ipa_from_nsp.py's steps (imported, not copied)
  ▼
nxnative/  (our fork of seedds/nxnative + the Android port)
  ├─ dm/host, dm/gfx, dm/tools        core: Horizon host, NVN layer, rewriter, shader split   (shared with iOS)
  ├─ dm/android                       core: Android runtime (Vulkan backend, front end, build.py, mkapk.py)
  └─ dm/games/<title ID>/             profiles: game.tsv + shader tables (+ patches.py) + android.tsv
```

## Layers and their rules

| Layer | Where | Holds | Must not hold |
|---|---|---|---|
| **Core, shared** | `nxnative/dm/{host,gfx,tools,third_party}` | What every game and both platforms need. Android differences behind `DM_ANDROID` / `__APPLE__` / `DM_TARGET`. | Game-specific branches. |
| **Core, Android runtime** | `nxnative/dm/android/` | Vulkan replay backend (`gfx_vk_*`), the OpenGL ES layer for GL games (`gl_android.c`: the device's EGL and GLES driver), the NativeActivity front end (on-screen gamepad, pause menu, settings, the save manager's export and import, text entry with a controller keyboard or an opt-in Android IME, haptics, shaking the device as shaking the controller, audio, performance hints), the NDK build (`build.py`), the APK writer (`apk/mkapk.py`), the Vulkan shader bundle (`tools/shader_vk.py` makes it; `tools/dmsv.py` holds its format, writes it with each shader's SPIR-V zstd-compressed, and converts a bundle between version 1 and 2; `gfx_vk_shader.c` decompresses a shader when it is first made, with zstd's decompressor in `dm/third_party/zstd`), the profile's Android header (`tools/android_profile.py`), the gamepad's layouts (`overlay_default.tsv`: tablet and phone) and its themes (`themes/`: a sprite pack per design, and `themes.tsv`, the table of which game wears which; `themes/README.md`). | Code that depends on a game: no title IDs, game names or per-game branches in code (comments may name the game a rule was found with, as upstream's do). A game that needs something different gets a profile key. |
| **Game profile** | `nxnative/dm/games/<title ID>/` | Data only: `game.tsv` (upstream keys), shader tables, `patches.py` (per-build rewriter cuts), and `android.tsv` (Android keys, below). | Code paths. |
| **Port pipeline** | `porter/` | The stages that turn game files into the APK and data pack; the toolchain check; the profile registry; installing over adb. Runs headless. | UI. |
| **GUI** | `gui/` | Screens over `porter`: setup check, game folder, profile status, options, progress, install. | Pipeline logic: everything it does, the CLI does too. |
| **Distribution** | `packaging/` | The player's bundle (`build_bundle.py`, PyInstaller): one executable that is the GUI and the Python the pipeline runs the engine's tools with (`nx2android.py`), the committed `nxnative/` beside it, the install guide (`INSTALL.md`). | Pipeline logic or toolchains. |
| **Dev tools** | `devtools/` | Scripts for bringing up a game on a connected device (pushing files, screen recording, soak tests, pass traces). The device comes from `devtools/device.json` or `NX2A_DEVICE`. | Anything the port needs. |

The game profile is compiled into the host (`game_profile.h` and `android_profile.h`, generated by `build.py`), as upstream does: porting a game builds its host with the player's NDK, which takes seconds.

The Vulkan pipeline cache is a writable driver product under `DM_ROOT`, separate
from portable shader assets. Its envelope validates renderer ABI, device/driver
identity, length and digest before driver creation. Legacy raw files retain the
Vulkan version-one vendor/device/UUID check and migrate at the next save. Saves
serialize through one I/O lock and fixed temporary name, publish atomically, and
skip identical content by digest; incomplete snapshots and publication failures
remain retryable. The legacy path cannot provide integrity guarantees absent from
the old format.

Vulkan descriptor collection checks each image binding against its 384-entry
scratch array before writing it. A binding that would exceed capacity stops the
host with a diagnostic; valid arrays keep their full reflected counts, including
the existing 32-entry default for a zero count.

Immutable Vulkan driver segments share submission scratch only when both their
hash and exact content match in the current epoch. Equality reads a CPU snapshot
of the live c0/c2 prefix (0x648/0x968 bytes), avoiding reads from mapped GPU memory.
A cross-bank hash collision compares the longer prefix, including the shorter
bank's implicit zeros. The 1,024 CPU snapshots cost about 2.35 MiB of content;
GPU-written segments must not enter this cache. This is a correctness guarantee,
not a measured device performance result.

CPU-decoded Vulkan descriptors preflight tracked GPU writes before allocating command scratch or descriptor sets. Later deferred inline updates can cover dependencies from either the open or a prior submission without a wait. GPU-write records stay fence ordered and checks visit only the live suffix, newest first; the newest uncovered dependency determines the one completion wait or internal submission cut. A wait includes copied-pool readback. `DM_VK_CPU_READY=0` disables this readiness path, including linear-target pass endings, for live diagnostic comparisons; it defaults on and is refreshed each submission. This control can expose stale CPU reads and is not a game-profile optimization.

Direct indexed quads retain first-byte pool eligibility while preflighting the entire declared CPU index range, including spans crossing registered pool chunks. An index address outside the pools skips readiness and reaches the draw path's existing rejection diagnostic; arithmetic overflow is rejected during preflight. After readiness, one deferred-aware read fills a replay-thread-owned heap snapshot. It grows to the largest input seen and stays allocated until process exit; conversion selects the index width once and uses aligned typed loads from cached CPU memory, and only the expanded GPU index output uses Vulkan scratch. Unaligned guest input remains supported by the snapshot copy. Native GPU-index and indirect paths retain their existing behavior.

Vulkan pools that cannot use zero-copy keep a CPU snapshot of their synchronized GPU buffer. At completion only bytes changed by the GPU against that snapshot are merged back, preserving independent CPU writes made after synchronization, including writes in the same page. Mapped results are read through a 4 KB CPU buffer before byte comparisons, avoiding repeated byte reads from GPU-mapped memory. The existing cached/uncached pool coverage rules stay in place; a device-to-host memory barrier precedes completion. After a full completion merge, the next incremental sync refreshes only the snapshot blocks it uploads; initialization and untracked pools retain full snapshots. NVN CPU_UNCACHED pools merge only their tracked GPU-write ranges and keep the baseline complete after every merge, as they trusted those ranges before the baseline: an untracked GPU write stays in the GPU copy until a later tracked range over it merges it. A full snapshot at the next sync instead would copy the whole pool before every submission (Unicorn Overlord's 860 MB CPU_UNCACHED pool). The snapshot costs one extra byte of RAM per copied-pool byte and is freed with the pool; zero-copy pools need no snapshot. Games still have to synchronize CPU and GPU writes to the same bytes.

Copied pools can opt into host-cached memory with `DM_VK_POOL_CACHED=1` (off by default). A cached allocation is published only after allocation, mapping and binding succeed; failed attempts release their resources and fall back to the existing host-coherent path (device loss remains fatal). Non-coherent pools flush once per uploaded pool before any submission part is sent: initialization covers the whole mapping, while incremental uploads flush the interval from the first changed block to the last, rounded outward to `nonCoherentAtomSize`. Clean gaps between changed blocks may remain in that interval. A range that reaches the pool tail uses `VK_WHOLE_SIZE` from its aligned start to avoid exceeding the allocation. After the GPU-to-host barrier and completion wait, they invalidate before merging results. With eligible range readback, each pool invalidates one atom-aligned interval spanning its clipped GPU-write ranges, or skips invalidation if none intersect. Other submissions invalidate the whole mapping. Each pool owns and maps its whole allocation; a tail range uses `VK_WHOLE_SIZE` from its aligned offset. Cache-maintenance failure stops the host rather than continuing with stale data. Zero-copy pools and other buffer allocations retain their existing paths.

`DM_VK_POOL_READBACK_RANGES=1` independently opts cached guest pools into range-limited completion merges for submissions containing only known transfer writes and read-only shader descriptors. Writable/unknown shader descriptors (checked before descriptor memo returns), transform feedback and texture-to-guest-buffer writes disable the mode for the whole submission. Uncertain submissions keep full cached-pool merging and whole-mapping invalidation. Eligible ranges keep the baseline complete for both cached and NVN CPU_UNCACHED guest pools because all device writes are covered. Outside the covered writes the GPU copy and baseline stay unchanged; their next tracked sync overwrites whole dirty blocks from guest memory before refreshing those baseline blocks. Uncertain CPU_UNCACHED submissions merge their tracked ranges, as with the switch off, and initialization/untracked pools still copy whole. Both switches are off by default. New GPU buffer-write paths must either register their full destination or force the conservative fallback.

Vulkan indirect compute dispatches copy their three GPU-written group counts into submission scratch memory in command order. A shader that reads c0 gets a private driver segment, outside the immutable segment cache, with the counts at `c0 + 0x200`; the dispatch reads that same record. Without c0, only a 12-byte record is allocated. Argument records may cross chunks of the same pool, with each chunk's buffer offset preserved. All words are validated before any argument copy, and a transfer barrier makes the record visible to both uniform reads and indirect dispatch. Scratch storage is retained until the submission completes. Direct compute dispatches and other driver segments retain their existing content caching.

## Game profiles on Android

A profile is offered for Android when it has an `android.tsv`; the profiles without one (52 of the 54 today, upstream's iOS games) show as "ios only": an experimental port can still try them. `android.tsv` holds, one `key<TAB>value` row each:

| Key | Meaning |
|---|---|
| `status` | `playable` (tested end to end on a device), `wip` (plays on a device, but parts are missing: README.md's Games table says which), `boots` (starts, not playable yet) or `experimental` |
| `tested` | `<version> <device>`: the version and device the status was checked on |
| `package` | The app's package name (default `org.nx2a.t<title ID in lowercase>`) |
| `orientation` | `landscape` (default) or `any` |
| `requires` | Device features the game needs, checked by the installer: `bcn` (BC texture compression) |
| `sysdata` | System data titles the game reads from the console's firmware, 16-digit hex title IDs (`0100000000000802`: MiiModel, the Mii heads Mario Kart 8 Deluxe builds): the port extracts each from the player's firmware dump (`--firmware`) into the data pack's `sysdata/<title ID>/`, and the host mounts it (`DM_SYSDATA`, `dm/host/hle_fs.c`) in place of its stand-in. Never shipped with the tool |
| `setting` | `<name>=<value>`: the pause menu's defaults on first launch (`overlay`, `rumble`, `docked`, `fps`: the frame rate counter in the top left corner, off by default; `opacity`: the gamepad's, 20 to 80 percent by 5, 60 by default), written to the data pack's `settings.txt`, where the app also keeps the player's own gamepad layout from the pause menu's layout editor (`ui=` rows) and its Snap to grid (`grid`, off by default) |
| `env` | `<KEY>=<VALUE>`: a host switch the game needs on Android, written to the data pack's `env.txt` |
| `overlay` | `<tablet\|phone> <control> <x> <y>`: moves one on-screen control of that layout (`dm/android/overlay_default.tsv`) to x, y as fractions of the window, compiled into `android_profile.h` |

Per-build knowledge stays where upstream keeps it: the rewriter's cuts in `patches.py` / `dm/tools/sdk_patches.py`, keyed by build ID.

## The port

`python -m porter port <game folder> -k <prod.keys>` (the GUI's **Port** button) runs these stages. The slow ones (extraction, rewrite, shader split, the translator build, the Vulkan shaders) keep their output with a key of their inputs and are skipped on the next run when the key is unchanged; the host build is incremental (`build.py`), and the APK and the data pack are made again each time (seconds).

Shader reuse checks the generated bundle against its receipt. Windows uses size
and modification time for the fast path. POSIX also checks change time and file
identity. A metadata change triggers a digest check. On Windows, a same-size
edit that preserves the original modification time can pass the fast path.
Translator output trees are checked by relative name, size and hash, including
dependencies. The exporter records expected keys and stages and failed keys and
reasons in `android/shaders.dmsv.report.json`. Individually valid products from
interrupted batches can still be included. The porter accounts for every
expected shader and requires at least one emitted shader before publication.
Partial bundles are reused when their inputs are unchanged, with the failure
count in the receipt note. The report is published before the receipt and its
digest is checked on reuse. A changed input or missing or changed report
triggers translation. The shader key covers the three Android export helpers
(`shader_vk.py`, `dmsv.py`, `shader_products.py`), the shared shader tools, profile,
captures and translator. The new receipt format rebuilds existing ports once.

| Stage | What | Output (in `<game folder>/<title ID>_build/`) |
|---|---|---|
| inputs | Find the base game, updates and DLC (NSP / XCI / NSZ / XCZ files, regardless of extension case), match the profile, pick the version; check the game folder's drive has room (about twice the game files, NSZ / XCZ counted decompressed and once more for their NSP, less an earlier port's build folder) | |
| decompress | Only with NSZ / XCZ files that a stage below will read (a reused extraction reads none): each becomes an NSP (an XCZ: an NSP of its secure partition, with or without the leading 0x1000-byte card key area), its NCZs expanded and encrypted again with the keys their section tables carry, every NCA checked against its SHA-256 name (`porter/dumps.py`). Deleted once the DLC are extracted, or when the port fails | `tmp/dumps/` (temporary) |
| extract | `nx_extract` (built with the .NET SDK); XCI cards may also retain their leading 0x1000-byte key area, and an NSP's PFS0 header takes precedence over card-magic bytes in its payload | `extract/<version>/{ExeFS,RomFS}`, `aoc/` |
| system data | Only for a profile with `sysdata` and a `--firmware` folder (the player's own system content files, `.nca`): `nx_extract --sysdata` writes each title's RomFS; without the folder the port says so in red and the host's stand-in is used | `sysdata/<title ID>/` |
| 60 fps | Only with `--fps60` (below): the profile's own cap, or the build's FPSLocker-Warehouse config converted for the host | `android/fpslock/{fpslock.tsv,patches.py,<build ID>.yaml}` |
| rewrite | `patch_nso.py` with `DM_TARGET=android` | `android/patched_<version>/` |
| shaders | `shader_split.py` (the DLC's own shaders too, `aoc/` given as `DM_SPLIT_AOC`), then `shader_vk.py` (SPIR-V, each module zstd-compressed in the bundle: 3.5x smaller, about 2 s more for the largest bundle; uncompressed in a Python without zstd) with the translator built from the repository's source (`dm/gfx/tools/dmsh_xlate` over `dm/third_party/ryujinx`, once per player in their nx2android folder), plus the shaders captured on the device (below) | `shader/pkg`, `android/shaders.dmsv`, `android/captured_shaders/` |
| host | `dm/android/build.py --release` with the player's NDK (`--debug`: a development build, debug information and `DM_CTL`) | `android/host/libdmhost.so` (`android/host-debug/`) |
| apk | `dm/android/apk/mkapk.py`, signed with the player's own key, with the game's gamepad theme only (`dm/android/themes/themes.tsv`: its pack, else the ergo pack) as `assets/overlay/`, and the overlay's font with its licenses (`dm/third_party/fusion-pixel-font`) as `assets/font/` | `<out>/<App>.apk` |
| data | The files the app reads from `/sdcard/Android/data/<package>/files` | `<out>/<App>-data/{mods,RomFS,aoc,sysdata,shaders.dmsv,nintendo_ext.ttf,env.txt,settings.txt,nx2a-data.json}` (+ `fpslock.tsv` with `--fps60`); the button-icon font is made in `android/font/` |
| install | `adb install`, the profile's `requires` checked against the device, the data pack pushed (optional); `--romfs-at`: the RomFS read from a folder already on the device (below) | |

An NSP or XCI contains NCA entries. If LibHac cannot open an entry's header,
`nx_extract` names both the input container and the NCA entry, includes LibHac's
reason, and stops with exit code 4. This diagnostic does not establish whether
the input or the keys caused the rejection. `--allow-damaged` does not bypass
header failures; filesystem integrity errors keep their existing handling.

RomFS in the data pack is hard-linked to the extraction when the volume allows it, so it takes no extra space.

`--vulkan-driver <lib.so>` packs a Vulkan driver (Mesa's Turnip) in the APK under a `lib*.so` name, beside libadrenotools and its hook libraries, and the data pack's `env.txt` names it (`DM_VK_DRIVER`; `gfx_vk_core.c` loads it through adrenotools, and falls back to the device's driver when it does not load). `python -m porter driver <lib.so> [--package …]` changes the driver of a port already on the device without the game's files (`porter/driver.py`): the installed APK is pulled, written again by `dm/android/apk/apkdriver.py` with the new library in place of the old (every other entry kept, page-aligned and signed again with the player's key by `apksign.py`, the ZIP writer and v2 signer `mkapk.py` uses), installed over the app (its saves stay), and `env.txt`'s `DM_VK_DRIVER` row names it; `--system` drops the library and the row (the device's driver). An APK ported without `--vulkan-driver` has no libadrenotools and is refused: it needs one port with a driver first.

`python -m porter host [--package …]` brings a port on the device to this checkout's host without the game's files (`porter/host.py`): `libdmhost.so` is built again by `dm/android/build.py` from the repository's profile (the title ID from the data pack's `nx2a-data.json`; a debug build for a debuggable app) and put in the installed APK by `apkdriver.py --host`, the driver library kept, with the overlay's font and its license files (`assets/font/`, `pipeline.ui_font_assets`; `--asset` replaces or adds them), which an APK ported before the font came lacks. The game's rewritten modules on the device must fit it: `mods/build_src.sha256` (patch_nso.py) holds the hashes of the rewriter and the patch files that made them, and when any of them differs from this checkout's (the rewriter, `sdk_patches.py`, the game's own `patches.py`, or patches registered for it since) the update is refused and the game needs a port again; other games' patch files are keyed by their own build IDs and do not count, and a changed `sdk_patches.py` does not either when it and the game's `patches.py` still give each of the port's modules (by the build ID in `mods/<module>.cuts.tsv`) the cuts and observation gates its `.cuts.tsv` and `.obs.tsv` list, as after a cut added for another SDK build. The port must also have been made from the repository's profile, since `DM_GAME_MEM_ALIAS` and the rest of `game_profile.h` are compiled into `libdmhost.so`: its version (`nx2a-data.json` `version`) must be one the profile's `build` rows register, and `nx2a-data.json` `profile_h` (the sha256 of the `game_profile.h` the port's host was built with, which `porter port` writes) must equal this checkout's; a derived profile's port (a version the profile does not register, with its automatic alias headroom, issue #26), an `--alias-headroom` port, a profile changed since and a pack from before `profile_h` are refused, and the game needs a port again. The title ID must be 16 hexadecimal digits. Nothing else in the data pack changes (`env.txt`, `shaders.dmsv`): a new shader translator or profile row needs a port again.

## Android text input

`hle_swkbd.c` handles the guest's encodings and length limits. The Android front end dispatches Java keyboard requests through `keyboard_android.inc`. Each request runs JNI on a short-lived host pthread because a non-main guest thread can run on a stack outside its pthread stack range. The guest joins the worker before using the result or falling back to the controller keyboard when the optional Java method is absent.

## Saves

The app keeps the game's save in its internal storage (`$DM_SAVE`, and `<DM_SAVE>_device` for a game that mounts a device save too: `hle_fs.c`), which a reinstall keeps, an uninstall deletes, and adb cannot read in a release build (it is not debuggable). The save manager (`dm/android/saves_android.c`) copies it in and out through the app's files folder, which adb, porter and the PC reach without a permission:

- `saves/<YYYYMMDD-HHMMSS>/`: one export, the save's files byte for byte, as a console's save tools copy them (so a console's save folder imports as it is, and an export goes back to a console the same way); `saves/<name>.device/` beside it holds the device save.
- **Export save** (the pause menu's Game tab) copies the committed save (never `.work`: a transaction in flight is not a save) on a thread of its own, through a hidden `.part` folder renamed when whole, and starts again if the game commits meanwhile.
- **Import save** opens a picker of the folders in `saves/`, newest first. The import is applied at the next start, before the host mounts anything (`ANativeActivity_onCreate` → `dm_saves_start`), so it never meets a commit: the menu writes `saves/import.txt` and the app ends. At the start the save it replaces is exported first (`<stamp>-before-import`), the folder is copied to `<DM_SAVE>.import` and swapped in with one `renameat2(RENAME_EXCHANGE)`.
- `porter saves` (the GUI's **Saves** tab) does the same from the PC: `apps`, `list`, `export [dest] [--name …]` (a fresh export: the app is stopped and started with `saves/export.txt`, exports and ends without starting the game, then the folder is pulled), `import <folder or .zip>` (pushed under a hidden name, renamed, named in `saves/import.txt`, and the app started to apply it). Each request carries a token the app writes back in `saves/result.txt` with its outcome.
- The files are not changed. A save made on a console belongs to that console's user; a game that keeps its user's id inside its own files (Animal Crossing: New Horizons, issue #16) reads it as another user's, since the host's one user (`hle_account.c`) is not mapped into it.

An Android shader profile can set `android_dynamic_slots` to `on` in `game.tsv` to bind separate texture and sampler arrays from the driver slots (requires `tex_dyn_slots on`). `android_subgroup_size` selects the translator's subgroup size; its default is 128. For a packed texture handle read directly from game memory, `android_shader_handles.tsv` gives the shader key, guest handle, replacement slot handle and expected number of sites. The shader builder applies these rules to the translated game shader and checks the site count. Paper Mario: The Thousand-Year Door uses this for the animated save block on Adreno 840.

Shaders captured on the device: a game can set shaders whose code is in no game file (Xenoblade Chronicles 3, hundreds: effects and model materials), which the split cannot find. When a draw needs a shader the bundle lacks, the app saves it to `captured_shaders/<key>.bin` in its files folder (`gfx_vk_shader.c` `vk_shader_missing`; the draw is skipped this time). A port with `--install` first pulls that folder into `<build folder>/android/captured_shaders/`, which is kept from port to port, and `shader_vk.py --capture` translates it into the bundle. These shaders are not in the profile's tables: the tables stay what the game files give. So such a game draws everything only after it has been played that far once and ported again.

Unity serialized resources can omit their type trees. The shader reader borrows an embedded tree of the same class and type hash, or uses an exact-hash layout in `dm/gfx/tools/unityfs.py`; it never selects a layout solely by the Unity version. The Unity 2020.3 ComputeShader fallback reads keyword-set `variantMap` entries, including built-in skinning and blend-shape kernels. These are package shaders, not runtime-only captures: rebuilding from the original game files supplies them without first playing the game. A missing-layout report is a reader coverage gap, not proof that the shader code is absent from the game files.

Captured compute code can be headerless: `shader_vk.py` uses the same control-section thread-group rule as `shader_split.py` to identify it. Compute translation jobs take local dimensions and shared-memory size from that control section before applying the profile's facts, so captures without a facts-table row do not silently become `1x1x1` kernels.

Capture coverage is scene-dependent: a first-room check does not cover other maps, and a missing compute shader can leave later rendering inputs unwritten even when every draw has a program. Before promoting a shader bundle, pull the current device captures rather than reusing an earlier snapshot, check that every valid captured key is included, and exercise the affected map transition. Keep the previous bundle for rollback until that scene is verified.

The install starts the app once before pushing anything: Android makes the app's files folder, owned by the app with the app's group, when the app first asks for it, and a folder the shell makes first lacks that group underneath FUSE, so the app cannot read what is pushed below it. Files whose path passes Windows' 260 characters are pushed through short hard links (adb.exe is not long-path aware). A file already on the device at its size is skipped; the port's own outputs (everything but `RomFS/` and `aoc/`, which change only with the game's version) are also compared by MD5, because a rewriter cut changes a module without changing its size.

Large files are pushed in 64 MiB pieces. After an interrupted push, a piece is reused only when its size and MD5 match the current source chunk; a missing checksum or different content makes it transfer again. Retained pieces are checked in small batches, and a failed checksum command leaves the remaining unverified pieces to be sent again. This reads the local chunks and the retained device pieces without loading the whole file into memory. Joining uses only the current file's numbered pieces, so a shorter replacement or changed chunk size cannot append old pieces. A short read or a source-size change stops the push before joining; the source must remain unchanged during a transfer.

**A RomFS already on the device** (`porter install <App>-data --romfs-at <folder>`, or `porter port … --install --romfs-at <folder>`). The RomFS is most of a game (7 to 18 GB), and a player who also plays the game in an emulator on the device has it there already, in the dump's folder. With `--romfs-at` the app reads that folder instead of a copy in its files folder: env.txt's `DM_ROMFS`, which the host mounts as `rom:` (`hle_fs.c`; its `fs mount rom: → <folder>` line in the log shows the folder).
- The folder must hold exactly the pack's RomFS: the same paths and sizes, listed as the files folder is (`remote_sizes`), and the same content for a sample of up to 256 files of at most 4 MB spread over the paths (MD5, `romfs_sample`): a dump of another game version whose changed files kept their sizes passes the listing. A device that gives no MD5 gets a `[RED]` line and the listing alone. One that differs is refused before the APK goes in, with the first differences of each kind, unless `--romfs-push` asks for the pack's RomFS to be pushed into it (an empty folder, a folder on the SD card); the push adds and replaces files but never deletes one, so a folder holding files that are not the game's is refused either way.
- Only shared storage (`/sdcard/…`, `/storage/…`), and no folder under an `Android/data` or `Android/obb`, which Android keeps from every other app whatever its permissions.
- The APK asks for All files access (`MANAGE_EXTERNAL_STORAGE`) and, for Android 10, which has none, `READ_EXTERNAL_STORAGE` up to API 29 with the legacy storage view (`requestLegacyExternalStorage`, ignored from Android 11): `mkapk.py`. Both stay off until granted, and the app never asks for them, so a port that reads its files folder runs as before. The installer grants the access over adb (`appops set --uid <package> MANAGE_EXTERNAL_STORAGE allow`; `pm grant` on Android 10), reads it back, and stops before pushing anything when it did not take, naming the switch in Settings. For an update of an app that already asks for the access, the grant (the app's uid's, which the update keeps) comes before the APK, so a refusal leaves the old APK and data as they were; a new app is granted after its install, with no data yet. An APK made before this asks for neither and is refused: port again.
- The pack's RomFS is not pushed into the files folder and not counted in the free-space check (the files `--romfs-push` puts in the folder are, when the folder is on the same volume: `same_volume`, `stat -L` through the `/sdcard` link), and a copy an earlier install left there is deleted, after env.txt points at the folder.
- The row `DM_ROMFS=<folder>` goes into the device's env.txt under a `# porter install --romfs-at` comment, after the pack's rows (the app applies them in order). The folder is a fact of one device, not of the pack (one pack can go on two devices that keep the dump in different places), so the pack never holds it: each install without `--romfs-at` reads the row back from the device's env.txt, compares the folder with the new pack again (a port of a later game version needs the later version's RomFS) and writes it again; the GUI's **Install on device** does the same. `--romfs-at app` moves the RomFS back into the files folder and drops the row; the folder is left as it is.
- The DLC (`aoc/`) stays in the files folder: it is small for most games and laid out by the port (one folder per DLC index), not as a dump keeps it.
- The pack on the PC keeps its RomFS (hard links to the extraction: no space of its own), which is the list the installer compares the folder with; a port without it would have nothing to check against, so there is no such option.

At launch the app checks a `DM_ROMFS` outside its own folders before the host starts (`front_android.c` `romfs_readable`): without the access it logs a `[RED]` line that says so, opens Android's All files access page for itself (Android 10: its app info page) and ends; a folder that is not there (an SD card taken out, a dump moved) gets a `[RED]` line and ends the app too.

OpenGL ES games (FM24 Touch: NVIDIA's OpenGL driver in subsdk0, GLSL ES shaders compiled at run time): the port skips the shader split and the Vulkan shaders and packs no `shaders.dmsv`; on the device `gl_android.c` takes the game's EGL calls and hands its GL calls to the device's own OpenGL ES driver, each on the calling thread's big host stack, decodes BC textures on the CPU (OpenGL ES on Adreno has none), and shows each frame through the Vulkan present path (`vk_present_vkimg`, an AHardwareBuffer the GL frame is blitted into), so the gamepad overlay, the pause menu and the pacing stay as for NVN games.

What the port refuses: a game whose `main` renders with Vulkan (the Android host replays NVN and runs OpenGL ES so far), and one whose shaders need a step upstream runs by booting the game in the Mac host (GLSLC capture, legacy Unreal paks, PlatinumGames' PKZ archives).

**Oodle on the device.** Shaders that only the game's own Oodle decodes are decoded with that code on the Android device: the host built as an executable (`build.py --exe`) and the rewritten modules go to `/data/local/tmp/nx2a-oodle` once a port, each job file is decoded there (`dm/host/hle_oodle.c` `DM_OODLE_JOB`), and the folder is removed afterwards (`pipeline.device_oodle_job`). So the port needs adb and the device even when it does not install. Game Freak's GFPAKs and Trinity packs go as one job before the split (`device_oodle`). The returned result is indexed by file offset and length, then copied into the split's decoded archives in chunks of at most 1 MiB, without retaining whole payloads or concatenated archives in Python memory. Short headers, record lengths and payloads fail the stage before decoded archives are written. The temporary result is removed after copying and closing it. Unreal Engine's shader code archives (version 11 paks, Unreal Engine 5's IoStore shader libraries) go in rounds (`device_ue`): `uepak.job` runs with a decoder that answers from what is decoded so far and notes the rest, the noted streams go to the device as one job, and the next round runs, until a round notes nothing (FINAL FANTASY RESONANCE: one round of 5,919 shader groups, 74,244 shaders in under a minute); the archives land in `<version dir>/ue_shaders` with the NSP script's stamp, where the split reads them, as the Mac's `decode_ue_shaders` leaves them.

**Versions.** The newest version in the folder is packed. A version the profile was not brought up on is packed from a derived profile (upstream's `derive_profile`, in `profile-derived/`), without that version's per-build fixes. When another build is packed (GitHub issue #26):
- a profile that declares virtual address memory (a `sys_resource` row, not 0) gets 8 GB more `mem_alias` and `mem_reserve` in its derived copy (`pipeline.alias_headroom`): the address regions such a game reserves depend on its build (Donkey Kong Country Returns HD's base game reached +7.0 GB of alias region, where its tested update stays under +2.75 GB), the tested build's high-water mark does not bind another one, and the heap and the device's memory stay as they are;
- a module whose build has no registered patch, where the tested build of it has some (`dm/tools/sdk_patches.py`, the profile's `patches.py`), gets a `[RED]` line that names the patches it goes without (`pipeline.lost_patches`).

`--alias-headroom <GB>` (0 to 48; the GUI's **Extra address space**, Auto when not given) sets that headroom for any port of such a game: the derived copy, or for a version the profile was brought up on a copy in `profile-mem/` (without `patches.py`, which stays in `dm/games`), which every tool takes first. `0` keeps the profile's layout. It is for a game whose log shows `AllocateAddressRegion … refused (0x1803)` before it crashes; a game without virtual address memory keeps its layout whatever the value.

**Experimental ports** (`--experimental`, the GUI's Experimental box): a game without an Android profile. With no profile at all, upstream's survey (`<game folder>/<title ID>_survey/survey.md`) guesses a provisional one; with only an iOS profile, that profile is copied. Either way it goes to `<title ID>_build/profile/<title ID>/` with an `android.tsv` of status `experimental`, and every tool finds it there (`DM_GAMES_DIR`). That folder is where a bring-up starts; a game that works gets its profile into `nxnative/dm/games/`.

`--package` installs a port under another package than the profile's, beside the player's other build of the game (a test).

**versionCode.** The APK's versionCode is the packed Switch version number + 1 (v196608 → 196609), so a port of a game update installs over the base game's port. Android installs an APK over one with the same versionCode, but never over a higher one (`INSTALL_FAILED_VERSION_DOWNGRADE`); the only other way past that is an uninstall, which deletes the saves. `--vercode-offset N` (or `NX2A_VERCODE_OFFSET`) adds N, 0 to 65535, so a rebuild of the same version installs over an earlier rebuild with an offset; 65535 at most keeps it below the next version's port, as Switch versions are 65536 apart. A refused downgrade names the installed versionCode.

**Touch games** (`--touch`, the GUI's Touch game box). On Android the game's touch screen takes every touch in both modes, for every game (`hle_hid.c` `touch_on`), but the on-screen gamepad's controls take the touches that go down on them or near them (`front_android.c` `ctl_at`; about a quarter of a tablet's screen, at its sides), and the gamepad is shown by default. `--touch` writes `overlay=0` into the data pack's `settings.txt` over the profile's settings (`pipeline.TOUCH_SETTINGS`), as Unpacking's profile does: the gamepad starts hidden, only the menu button takes touches, and the pause menu shows the gamepad again. It is the first launch's default: the installer keeps a `settings.txt` the app already has. It costs nothing at run time (the host's touch reads are the same with the gamepad shown or hidden). A game that ignores touch while docked needs handheld mode too (the pause menu's mode item).

**60 fps** (`--fps60`). A Switch game capped at 30 needs per-build knowledge to run at 60: which memory holds its frame limit, or which code counts frames. A profile that has it (`fps_target`: the rewriter's frame-step stubs or `hle_fpslock.c`'s rows) gets `DM_FPS_TARGET=60` in `env.txt`. Otherwise the port fetches the community's config for the packed `main` build from masagrator's FPSLocker-Warehouse (`porter/fpslocker.py`; GitHub, `SaltySD/plugins/FPSLocker/patches/<title ID>/<build ID>.yaml`) and converts it: the `ALL_FPS` memory writes (pointer chains from `main`, compares; the expressions evaluated for 30 and 60) become `fpslock.tsv` in the data pack, which `hle_fpslock.c` writes on every present (`DM_FPS_LOCKS`); `MASTER_WRITE` bytes become cuts for the rewriter (`patch_nso.py` `DM_PATCHES_EXTRA`, original bytes from the game's `main`); presents follow the display (`DM_PRESENT_INTERVAL=display`), as FPSLocker paces them itself. A config using what the host lacks (`asm_a64`, `DECLARATIONS`, non-`MAIN` regions, `refresh_rate`) is refused whole; 1,160 of the 1,462 configs convert (2026-10-28). A missing, unavailable or refused external config adds no FPSLocker changes; built-in profile patches still apply during the rewrite, independently of `--fps60`. The external-config status does not say whether that device can sustain 60 fps. The warehouse has no license, so its configs are fetched per port and never committed. Whether 60 holds on a device, and whether the config fixes every speed issue, is the config's and the device's: it is the player's choice.

Events: with `--progress json`, every line on stdout is one JSON object, the protocol of upstream's NSP script: `stage`, `step`, `progress`, `stage_end`, `say`; `porter` adds `result` (the outputs) at the end. A line starting `[RED] ` in a `say` is an error or warning.

**Local play over the LAN** (`env DM_LAN=1` in a profile's `android.tsv`; off by default). Local wireless play (`nn::ldn`) runs over the Wi-Fi network the device is on, with the protocol of Atmosphère's ldn_mitm (UDP and TCP port 11452: a station broadcasts a scan, each host answers with its NetworkInfo, a station joins over TCP and the host sends every station the node list), so a port plays with Switches that run ldn_mitm and with other ports on the same network. `hle_ldn.c` answers `nn::ldn` and `nn::nifm` (a local-mode request is granted, an internet request stays refused), `hle_socket.c` puts `nn::socket` on the host's own sockets (Horizon's ABI: FreeBSD's sockaddr, option and flag numbers, Linux's error numbers and `O_NONBLOCK`), and `android/lan_android.c` holds a Wi-Fi multicast lock so broadcasts arrive. Parental controls allow free communication and `nn::friends` makes play history keys locally while it is on. With `DM_LAN` off every one of these stays offline, as before. `DM_LAN_TRACE=1` logs every socket call and every `nn::ldn` / `nn::nifm` query with its result. Online play (Nintendo's servers) stays out of scope.

## Android input

**Show gamepad** is saved in `settings.txt`. When enabled, the on-screen controls hide on a mapped controller button press or when stick, D-pad or trigger motion reaches the same activation thresholds as gameplay. A touch restores the controls for the next press, including while a controller is still attached. Button releases still reach the game but leave the restored touch controls visible. The last used controller disconnecting also restores the controls. When **Show gamepad** is off, only the draggable menu button is visible and all other touches go to the game. The menu button stays available in either mode. The controller count (`pad_watch`) is used for vibration routing.

## What the player installs

The player gets the bundle (`dist/nx2android-<version>-<os>-<cpu>.zip` from `python packaging/build_bundle.py`, for Windows and macOS): unzip, start `nx2android.exe` (`nx2android` on a Mac), nothing to install with pip. It does not ship toolchains; the Setup tab (`nx2android.exe -m porter doctor`, or `python -m porter doctor` from the repository) checks them and the free disk space, and its **Download missing tools** button (`porter tools --download`, `porter/fetch.py`) fetches the missing NDK, .NET SDK and platform-tools from Google's SDK repository and Microsoft's release list, checks each archive against the checksum its list gives, and unpacks them into the player's nx2android folder (`toolchains/`), which the finders search:
- **Android NDK r27c** (`ANDROID_NDK_HOME`, the configured path, or the usual install folders). The default build needs no Android SDK or JDK: `mkapk.py` writes and signs the APK itself. The optional `--external-display` and `--native-keyboard` activities additionally need `javac` and Android SDK platform and build-tools. External display alone uses `ExternalActivity`; combining both options selects `KeyboardExternalActivity`, which adds the IME to that activity. Installation and save requests resolve the installed launcher rather than assuming a particular activity class.
- **.NET SDK 10**: builds `nx_extract` and the shader translator, and runs them.
- From the repository instead of the bundle: **Python 3.11+** with `requirements.txt` (`lz4`, `capstone`, `pillow`, `fonttools`, and `PySide6` for the GUI): the port runs the engine's own Python tools (the rewriter, the shader split). The bundle carries that Python.
- **adb** (platform-tools), only to install from the tool.
- Their own **prod.keys**. Keys and game files are never copied into the repository or the app.

The player's settings, APK signing key and built translator live in their nx2android folder: `%APPDATA%\nx2android` on Windows, `~/Library/Application Support/nx2android` on a Mac, `~/.config/nx2android` elsewhere (`NX2A_HOME` overrides it). An app keeps the same signer across ports, so updates install over it.

## Adding a game

1. `python -m porter port <folder> --experimental --install`: the survey, a provisional profile and a first try on the device. Bring it up from there with the upstream tools and `devtools/` (docs in `nxnative/docs/agents`): the profile moves to `dm/games/<title ID>/`, fixes go into the core as general rules.
2. Add `android.tsv` with `status` and `tested`.
3. `python -m porter port` on its folder, install, play. Raise `status` to `playable` when it is.
